Security

Understand custody

Your keys stay on your computer.

Oak has no third-party audit. Your wallet stays on your computer; you review what it is about to do. The details below explain custody, authority and limits.

Version 0.3.0 makes Oak free to use on Robinhood Chain, with approval in chat, an optional daily spending limit in USD, oak connect, Upoch reads. Agent 1's public tracker is being prepared. Run oak --version to see the version you have.

Disclosures

Read details
  • Oak is free. Holding $OAK has no access perks. It uses exact approvals. Oak previews and simulates transactions before local signing. Signature-only typed-data actions are shown for confirmation without transaction simulation. Its local guard refuses unexpected token movements or approvals before transaction signing. By default you approve each transaction and signature-only action with a yes or no in chat. Oak sets no spending caps or allowlists and does not judge whether a trade is wise. You can ask for a daily spending limit of your own and change it any time by asking.
  • Not affiliated. Oak is independent and is not affiliated with Robinhood.
  • Region notice. Oak displays a region notice by default. Availability of third-party protocols and assets varies by jurisdiction; you are responsible for complying with the laws and platform terms where you live.

Where your key lives

Read details

The treasury and contract admin is the single-owner wallet 0x856bb126188bDB5e425D3ac9D59E9ffBD12e6ECf. One owner key can spend treasury funds and replace the price signer. There is no second-signature requirement. Key compromise exposes these powers; key loss can make treasury funds and administration inaccessible. It cannot spend user wallet balances. Safe support is an optional deployment profile, not the launch setup.

Oak is built so that your private key never leaves your computer and the Oak server never sees your key and never signs or sends a transaction: your swaps and deposits go straight from your wallet to the project.

1. The Agent Wallet on Your Computer

When you install @oakagentkit/addon, the wallet is created and stored locally in ~/.oak/wallet.enc (mode 0600 inside a 0700 directory owned by your OS user; symlinks and hardlinks are rejected):

  • Optional legacy generation (oak init): Generates a 256-bit (24-word) BIP-39 recovery phrase locally, displays it once on your terminal, and requires you to confirm three randomly chosen words before persisting ~/.oak/wallet.enc. After deriving the secp256k1 key, the mnemonic and key buffers are zeroed in memory (hdKey.wipePrivateData(), Buffer.fill(0)). Oak cannot recover a lost key, by design.
  • Encryption at rest: The 32-byte private key is encrypted with AES-256-GCM using authenticated envelope metadata (AAD binds version 1, cipher aes-256-gcm, and storage descriptor).
  • OS Keychain preferred; automatic file fallback, legacy scrypt:
    • By default, a random 32-byte data encryption key is stored in your persistent OS keychain via @napi-rs/keyring (macOS Keychain, Windows Credential Manager, or Linux persistent Secret Service).
    • If a persistent OS keychain is unavailable, oak init requires a passphrase of at least 12 characters and derives the 32-byte data key using scrypt (N = 131072, r = 8, p = 1, 32-byte random salt). Without a persistent keychain, unlocking the wallet requires entering the passphrase in your terminal each time.
  • Owner-run terminal boundary (why PTY checks alone are not authentication): oak init and oak export check process.stdin.isTTY === true && process.stdout.isTTY === true and refuse to run otherwise (run this in your own terminal, not through the agent). However, a local AI agent with shell access can allocate a pseudo-terminal (PTY). Setup is trusted because you run oak init and oak export in your own terminal, never through the agent, not because a TTY check exists. Running them in your own terminal keeps recovery words and exported private keys out of the AI's context window, prompts, tool results, and logs.
  • ERC-8004 identity linking and request-bound sessions (packages/addon/src/identity.ts, session.ts):
    • Before running action tools, your agent wallet sets up an ERC-8004 identity on IdentityRegistry (0x8004A169FB4a3325136EB29fA0ceB6D2e539a432) via oak setup (or MCP tool oak_setup). You can mint a new agent ID (oak setup register, which costs gas) or link an existing agent ID (oak setup link <agentId>, which needs no ETH). Oak is free to use.
    • When linking an external owner's agent ID (oak setup link <agentId>) or revoking a link as the owner (oak identity unlink --owner <linkId>), your terminal prints the EIP-712 OakIdentityLink typed data and prompts you with hidden input to paste only the owner's signature. The owner's private key is never asked for, and the signature is verified once by the server against current ownerOf(agentId) and never stored in ~/.oak/config.json or in the server's link store.
    • If the ERC-8004 NFT is transferred or burned, or if you run oak identity unlink (or MCP tool oak_identity_unlink), linked action access ends immediately and the add-on clears the saved identity from ~/.oak/config.json. If the identity status check fails because of an RPC or server outage, the add-on keeps your saved identity locally, pauses actions, and asks you to try again while read tools stay open.
    • Every session token (X-Oak-Session, 15-minute life) is signed by your local agent wallet and binds the verified { chainId, registry, agentId, linkId? } tuple plus an ephemeral secp256k1 sessionKey kept only in add-on memory. Every non-read request (every action tool call and identity challenge, link, or unlink) also carries X-Oak-Request, a 60-second single-use signature by sessionKey over the session hash, HTTP method, path, and SHA-256 request body hash. The server atomically consumes the request nonce before executing.
  • Local signing, chat confirmation, and journal (packages/addon/src/sender.ts, journal.ts):
    • loadSigner() exposes only frozen closures (signMessage, signTransaction, signTypedData) and wipes the raw key buffer immediately after constructing the account.
    • Server-built transactions pass local swap validators or requested-input outflow checks using the local simulation trace. Every action is prepared first by calling a listed common action tool (swap, send, lend, withdraw, borrow, repay, bridge) or oak_prepare with {"name": "<tool>", "arguments": {...}} (simulating without signing and returning a six-part summary, actionId, and UTC expiry for the agent to show in chat and ask yes or no) and executed by calling oak_execute with {"actionId": "<the exact actionId>"} after you say yes (re-running simulation and local guards, checking that terms have not worsened, checking the optional daily spending limit in USD, and signing locally). See the enforced checks and limits.
    • Every transaction sequence is serialized under an atomic per-wallet directory lock (~/.oak/<address>.lock), simulated first (preview), checked for sufficient ETH (value + gas * maxFeePerGas with 25% gas headroom), written to ~/.oak/<address>.pending.json before broadcast, and reconciled on the next run if interrupted.

2. The One Always-On Key: Price Signer

Across all of Oak, there is one always-on key: the price signer held by the Oak hosted service.

  • Sign-only, no funds, no admin: The price signer is sign-only, holds no ETH, never sends a transaction, and is separate from the treasury owner key.
  • Hosted custody: The price-signing key has read-only service permissions (0400). Only the hosted service and its host administrator can read it. The note issuer runs in the same process as the Oak server. It is separate from your local wallet key.
  • What it signs: It signs a signed 30-minute $OAK price note (PriceNote { wallet, oakPerEthE18, timestamp, nonce }) with a 5-minute life (300 seconds) and a single-use 32-byte nonce, bound by EIP-712 domain (OakPriceNote, version 1, chain 4663) to one caller wallet (msg.sender) and one consuming contract (OakBurner 0x660b86c5a3f9E1278cB5F01763fd0a630221C18B).
  • On-chain ETH/USD and the 50% guard: The price signer never sets a USD price on its own. ETH/USD is read on-chain by OakOracle from the 30-minute average (observe([1800, 0])) of the ETH/USDG pool (0x52e65B17fB6E5BA00Ed806f37Afcd2DaA50271Ca), and Oak assumes USDG trades at a dollar. OakOracle enforces a 50% guard, accepting a note only when oakPerEthE18 is within 50% of the live pool price (spot / 2 <= note <= spot * 3 / 2, read from Uniswap v4 PoolManager.extsload slot 6), and OakBurner enforces a 10% spot check (spot * 9 / 10 <= note <= spot * 11 / 10).
  • Rotation and pause: The single-owner treasury wallet can replace the price signer on OakOracle via setPriceSigner, and setting the zero address pauses pricing immediately on OakBurner. Notes signed by the old key are rejected from the next block.

Stolen-signer exposure and remaining risks

  • Burner chunk exposure: Each buyAndBurn chunk is capped at 0.5% of live pool liquidity and accepts at least note * 100 / 102 (with OakPricing.burnerMinOut applying a 49/51 output ratio). A bad note inside the guard band can make a chunk accept less $OAK than spot-fair pricing would imply (or in a single call if an attacker supplies just-in-time v4 liquidity to lift the 0.5% liquidity cap) until the treasury wallet rotates the signer.
  • Spot movement and compounding: At graduation depth (4.2 ETH locked), moving the live v4 spot price costs about $482 of capital for a 10% move and $7,236 for a 3x move (recorded round-trip scenarios). Anyone can pay to push the spot outside the guard so honest notes fail closed while displaced; a stolen signer combined with a spot move compounds because the guard is relative to spot.
  • ETH/USDG average: The sustained manipulation cost of holding the ETH/USDG pool's 30-minute average away from real ETH is unmeasured; this residual is accepted because market participants track real ETH.

3. Fee Income, Creator Fees, the Treasury Wallet, and the Burner Sweep Rule

  • Income and 25% buyback-and-burn: Oak takes a 0.25% fee on swaps and bridges (KyberSwap swaps, Velora swaps, and Relay bridges and swaps), plus partner referral fees (hood.ag registrations and resales, and Borro Bookrunners deposits), paid to the single-owner treasury wallet 0x856bb126188bDB5e425D3ac9D59E9ffBD12e6ECf. 25% of Oak's income buys back and burns $OAK: at least monthly, Oak converts 25% of the period's fee income to USDG, transfers it to OakBurner (0x660b86c5a3f9E1278cB5F01763fd0a630221C18B), fetches a caller-bound for: "burner" price note, and calls buyAndBurn in chunks of at most oracle.liquidityUsdgE6() / 200 (0.5% of live pool liquidity per call). Holding $OAK has no access perks. Oak uses 25% of its income to buy back and burn $OAK.
  • All 1.7% creator fees go to the launch wallet for development operations: $OAK is a standard Pons V2 coin paired with native ETH. Every trade pays 2% total: 0.3% to Pons and 1.7% creator fee (0.7% creator share + 1% creator tax, venue buybacks off). All 1.7% goes to the launch wallet (0x84b1B9e5D1cAfD9543E684BB39E9cbD478189EE2), which is the Pons creator-fee recipient and claims positive balances from the Pons fee escrow (0xd3AFEB2a57f70eF218Aa82451c51B2fb0416Ac9e) via owner-signed transactions.
  • Pons keeper dependency and external timelock: On graduated v4 pools, token-side fees reach the fee escrow only after Pons's own conversion keeper converts them (sweepPoolFees reverts InternalSwapRequiresOperator() while launch-token-side fees are pending), so token-side fees may be pending at any time. In addition, the external Pons owner (0x263ed295dAFaE1d9AAdD6E56c4B6F9f38eE019Dd) can propose replacing a token's creator-fee recipient subject to a 3-day public timelock that Oak cannot cancel.
  • Exact burner sweep rule: The single-owner treasury wallet can sweep stuck USDG from OakBurner to the single-owner treasury wallet only after a 90-day timer that it starts with a public on-chain transaction (armSweep, which requires a positive balance and records armedAt and armedBalance). A successful burn cancels (disarms) the timer only when the USDG it spends is at least the smaller of 1% of the armed balance (rounded up) and the most one burn call may take. A smaller burn succeeds but leaves the timer running, so this power is not limited to a broken burner. Calling sweepStuck() after 90 days moves at most the balance recorded when the timer was armed (min(balance, armedBalance)), so any USDG deposited after arming requires a fresh 90-day timer.

For the complete party-by-party permissions matrix, see docs/trust/authority.md .

Automatic Wallet Creation and Optional Backups

Oak creates a wallet automatically when oak mcp, oak address, or another wallet command first runs. There are no recovery-word challenges or passphrase prompts. The agent calls account, relays the public address and selected network, asks you to fund it with a little ETH for gas and USDG, then calls balances again after you fund it.

The private key stays local in ~/.oak/wallet.enc (AES-256-GCM, 0600, inside ~/.oak at 0700). A random encryption key is stored in macOS Keychain, Linux persistent Secret Service, or Windows Credential Manager when available. Otherwise Oak saves a random file key in the same owner-only directory (wallet-key-<id>, 0600). This fallback relies on your OS account and filesystem permissions: someone who can read both files can unlock the wallet. No passphrase is requested. Keep only the funds your agent needs.

Later runs reuse the wallet. A corrupt wallet or unavailable existing keychain never creates a replacement. Existing keychain and passphrase wallets keep their format; legacy passphrase wallets still need terminal unlock and cannot run piped MCP.

Backups are optional. When you hold more than pocket change, run oak export in your own terminal, never through the agent and keep the exported key offline. oak backup prints guidance without unlocking or exporting anything. Automatic wallets have no recovery phrase. oak init --recover accepts an exported private key or a legacy 24-word phrase, hidden in your terminal; --replace preserves the previous encrypted wallet. Oak cannot recover a lost key.

Key data flows from local cryptographic generation to authenticated local storage, then to frozen signing closures in the add-on. Only the public address, signing results and public transaction data cross into MCP/HTTP; raw keys and storage keys are not tool results. Wallets persist until the owner manages their files. Recovery replacement retains old encrypted bytes and the required keychain entry or file key; Oak performs no automatic wallet deletion or key rotation. File fallback encryption does not protect against a reader of the whole Oak directory.

Report a vulnerability

Reporting instructions

Oak is an access kit for Robinhood Chain (4663, 0x1237) and Robinhood Chain Testnet (46630, 0xb626). This repository publishes Oak's documentation, runnable examples, declarative recipe schema, and on-chain smart contracts. The CLI and MCP add-on (@oakagentkit/addon) and core module definitions (@oakagentkit/core) are distributed as built npm packages, and the hosted Oak service runs as a private service.

Oak is independent and is not affiliated with Robinhood.

Reporting a Vulnerability

Do not report security vulnerabilities in public GitHub issues, pull requests, discussions, or social channels.

  1. Primary channel — GitHub Private Vulnerability Reporting: Submit a private advisory at: https://github.com/OakAgentKit/oak/security/advisories/new
  2. Email fallback: If GitHub private vulnerability reporting is unavailable or does not fit your report, email support@oakagentkit.org.

What to Include

  • Affected target: Specify whether the issue affects the published npm packages (@oakagentkit/addon, @oakagentkit/core), the smart contracts in packages/contracts/ (OakOracle.sol, OakBurner.sol, or their libraries), or the hosted Oak service.
  • Version and environment: Include the exact npm package version, commit SHA, or deployed contract address and chain ID (4663 or 46630).
  • Reproduction: Provide minimal, self-contained reproduction steps or a standalone Foundry test (forge test) conducted against a local chain simulation of a mainnet state snapshot or Robinhood Chain Testnet (46630).
  • Impact: Explain how the issue violates the custody, authority, or pricing bounds documented in THREAT_MODEL.md, docs/trust/authority.md , and docs/trust/where-your-key-lives.md .

What Not to Post Publicly

  • Never post vulnerability descriptions, exploit proofs-of-concept, or unpatched findings in public issues, pull requests, or community channels before a fix is released and coordinated.
  • Never include private keys, 24-word recovery phrases, passphrases, session signatures, RPC URLs containing API keys, or personal information in any report, issue, or pull request.

Scope

In Scope

  • Published npm packages (@oakagentkit/addon, @oakagentkit/core):
    • Local wallet custody and signing: Any flaw that leaks private keys, recovery phrases, passphrases, or session credentials to prompts, tool outputs, logs, or network endpoints, or that bypasses eth_simulateV1 transaction previews, oak_prepare / oak_execute action-ID verification, chain-ID verification, exact-amount ERC-20 approvals, the optional daily spending limit, or the prepared-transaction signing window.
    • Declarative recipe handling (oak-recipe/v1): Any path that executes third-party code during oak recipes add or recipe execution, escapes ~/.oak/recipes/, follows symbolic or hard links, or bypasses the 64 KiB file, 4 MiB decompressed archive, or 100-entry limits enforced with packages/addon/schema/recipe.schema.json.
    • Continuation and untrusted-input validation: Any bypass of domain, wallet, stage, deadline, or hash verification during multi-turn EIP-712 RFQ continuations (meridian_buy, meridian_sell), or failure to strip control and format characters from untrusted external token metadata.
  • Smart contracts ( packages/contracts/ ):
    • Any bypass of caller-bound price-note verification (n.wallet == msg.sender), the 50% live-spot guard ([spot / 2, spot * 3 / 2]), OakBurner's 10% spot check, single-use note nonces, or the 90-day armed burner sweep timer (armSweep and sweepStuck in OakBurner.sol).
  • Hosted Oak service:
    • Authentication or replay-protection bypass on wallet sessions or single-use request signatures, entitlement bypass allowing action tools without a verified ERC-8004 identity, or price-note issuance outside the documented 30-minute window, warmup, and guard rules.

Out of Scope

  • User or agent signing choices: Signing a losing, illiquid, or malicious transaction after receiving its oak_prepare (or action tool) simulation summary, signing a signature-only typed-data action after reviewing its confirmation summary in chat, or importing and running an unreviewed third-party recipe (as-is, not reviewed by Oak). Oak sets no operator token allowlists or investment safety checks.
  • Accepted chat-approval residual risk: Because confirmation happens in chat (preparing with the action tool or oak_prepare, then calling oak_execute), an AI agent connected to oak mcp relays the person's yes and can call oak_spending_limit to change the daily spending limit immediately when instructed, as documented in THREAT_MODEL.md and docs/security.md .
  • Running terminal-only commands through an agent: Invoking oak init, oak export, or terminal owner-link signing through an AI agent or shell tool that allocates a pseudo-terminal (PTY) rather than directly in the owner's terminal.
  • Documented authority and economic residuals: The single-owner treasury and admin model (0x856bb126188bDB5e425D3ac9D59E9ffBD12e6ECf), the 0.5x to 1.5x oracle guard band and OakBurner 10% spot check, the 0.49x burner chunk floor and just-in-time liquidity cap interaction, spot manipulation costs on thin pools, and the external Pons owner's 3-day timelock on creator-fee recipients (0x263ed295dAFaE1d9AAdD6E56c4B6F9f38eE019Dd), as documented in docs/trust/authority.md and THREAT_MODEL.md.
  • Third-party infrastructure and protocols: Bugs or outages in the 33 third-party ecosystem protocols, external APIs, RPC providers, or the user's operating system and hardware.
  • Disruptive testing: Denial-of-service attacks, rate-limit exhaustion against live services, spam, or social engineering.

Response Expectations and Bounty Policy

  • Modest response targets: We review reports on a best-effort basis, aim to acknowledge receipt within a few business days, and follow up with a triage assessment once we reproduce the behavior.
  • Remediation and disclosure: Fix timelines depend on complexity and whether remediation requires an npm package update, a hosted service change, or a contract redeployment. We ask reporters to keep findings private until a fix or mitigation is available, and we credit reporters upon coordinated disclosure if desired.
  • No bug bounty: Oak does not operate a paid bug bounty program and does not offer or promise financial rewards for vulnerability reports.
