Claude Code · Codex · Gemini · Cursor · Grok

Mainnet: 4663. Testnet: basic tools and ERC-8004 identity only.

Subscriptions are open in Oak 0.2.6. Read tools need no identity or subscription; hosted actions require a verified ERC-8004 identity and an active subscription. Official $OAK address: 0x6511c233790Ec10f7d673c64DC82C3F941D57828. Pons page: https://ponsfamily.com/launchpad/0x6511c233790ec10f7d673c64dc82c3f941d57828. Plan availability follows account.phase: no-hold on the curve, neither plan during warmup, and both plans when ready with a valid price note.

Your agent's tool list shows the everyday tools. For anything not listed, it calls find_tool with what it wants to do, then run_tool with the tool's name and arguments. Tools run this way get the same access checks, local guard, preview and confirmation as a direct call.

Basics

Read details

Every amount crosses JSON boundaries as a decimal base-unit string (never a float). Every tool output identifies the token address, symbol, chain ID, and decimals. Non-read requests use request-bound sessions (X-Oak-Session plus a single-use X-Oak-Request signature signed by an ephemeral in-memory sessionKey). Before signing any transaction sequence, the add-on requests a preview (eth_simulateV1 with traceTransfers: true), reuses a matching preview from the same block within 12 seconds so swap does not re-simulate twice, builds exact token approvals only (never unlimited), and displays the simulated token deltas.

Buy a token (find_token → quote → preview → swap)

This swap example is for mainnet (4663). Testnet exposes basic tools and ERC-8004 identity tools; swap routes and the other ecosystem modules are not configured there.

  1. Find the token (find_token): Look up a token by name, symbol, or contract address on chain 4663 to confirm its verified address and decimals:
    oak call find_token '{"query":"TSLA"}'
  2. Quote the route (quote): Pass verified symbols (ETH, USDG, WETH, USDe, OAK, or an official stock ticker such as TSLA) or a verified token address from find_token, with amountIn in input token base units ("10000000" = 10 USDG with 6 decimals):
    oak call quote '{"from":"USDG","to":"TSLA","amountIn":"10000000","slippageBps":50}'
  3. Preview the simulation (preview): Simulate an unsigned transaction sequence via eth_simulateV1 to inspect exact token balance deltas (when you call swap, the local bridge also runs preview automatically before signing and sending): Template only — not runnable as shown. Replace ... with a complete unsigned transaction array from a transaction builder. A quoteId is not a transaction array. The local swap bridge runs the preview automatically before signing.
    oak call preview '{"txs":[...]}'
  4. Execute the swap (swap): Build, preview, sign locally, and broadcast the quoted swap using its 60-second quoteId:
    oak call swap '{"quoteId":"<quoteId>"}'

Find any other tool (find_tool, run_tool)

tools/list shows the everyday tools, such as status, swap, buy and sell, deposit and withdraw, and borrow and repay. Every other tool stays reachable by name. For anything not listed, call find_tool with what you want to do, then run_tool with the tool name and arguments.

  • find_tool searches every Oak tool, listed or not, by what you want to do, a project name or an exact tool name (query, with optional program and limit). It runs locally and only reads. Each match shows its name, project, whether it is a read or an action, whether tools/list shows it, a one-line description and its required inputs; an exact tool name also gives the full input schema.
  • run_tool runs any Oak tool by name through the same code path as a direct call, so the access gate, local guard, preview, exact approvals and human confirmation are unchanged. Reads still need no identity or subscription. Put the tool's inputs inside arguments.
  • An AI client that remembers "always allow" for run_tool lets it request every Oak tool. The local signing contract still requires human confirmation for value-bearing off-chain signatures. New lending actions, Hookr prepared actions, Relay vault exits and TickerSpring order accounting also require a person in auto mode.
oak call find_tool '{"query":"show my wallet history"}'
oak call run_tool '{"name":"history","arguments":{"limit":5}}'

Wave-3 integration installs the shared read gates, local transaction reconstruction and RFQ wallet lock. Meridian Predict buys are enabled; the bridge owns every continuation and signature, so never supply either manually. Meridian perps public reads and guarded deposit/finalize transactions are available, but perps signatures remain disabled pending their signing-contract expiry policy and registered local submission path. A deposit alone does not enable trading in Oak.

Hookr supports locally reconstructed fungible-token actions and current compounder actions. NFT/6909 grant-dependent routes remain blocked pending transfer tracing and approval journals. Signed referral registration remains blocked pending a declared relayed-signature policy; unsigned referral and other supported actions remain available. Collection-wide approvals and ERC-1155 custody are refused. Use hookr_contracts to fetch the exact schema before an action. Historical playbooks that say shared integration is pending should be read with these current limits.

  • oak init and oak export require a direct owner terminal (stdin.isTTY && stdout.isTTY).
  • oak setup sets up the wallet's ERC-8004 identity: oak setup link <agentId> links an existing agent ID using a gasless owner EIP-712 signature in your terminal, and oak setup register [--no-tag] mints and verifies a new agent ID on-chain.

Project recipes

Read details

Ecosystem builders can publish declarative JSON recipes (oak-recipe/v1) validated against packages/addon/schema/recipe.schema.json. Each recipe names one contract on chain 4663, one ABI function item, typed inputs, and kind: "read" | "tx". The add-on's importer (oak recipes add) is strictly data-only: it streams tarballs with a 4 MiB / 100-entry cap, ignores non-recipe files without writing or executing them, copies only package/recipes/<name>.recipe.json (max 64 KiB each) where project matches package/package.json's oakProject, and never executes third-party code. Recipes are opt-in by name (<project>.<name>) and labelled as-is, not reviewed by Oak .

Hard Custody Boundaries for Agents

  1. Wallet creation is automatic on first MCP/CLI wallet use. Call account, relay the public address/network, ask the user to fund ETH and USDG, then re-check balances. Backups are optional: oak backup gives guidance. Never run oak init or oak export inside an agent tool call. Both commands must be run by the human owner in your own terminal, never through the agent. Even if an agent can allocate a PTY, the security boundary is human execution so recovery words and private keys never enter agent context, prompts, or logs. Your private key never leaves your computer, and Oak cannot recover a lost key.
  2. Never ask the user for a private key, seed phrase, passphrase, or raw owner key. Both the local bridge (packages/addon/src/bridge.ts) and the Oak server reject any JSON argument containing private_key, secret_key, wallet_key, mnemonic, seed, seed_phrase, or recovery_phrase. When linking an external owner's ERC-8004 agent ID (oak setup link <agentId>) or revoking by owner (oak identity unlink --owner <linkId>), the owner signs the EIP-712 OakIdentityLink challenge in their own terminal (Owner signing requires your terminal. Run oak setup link <agentId> or oak identity unlink --owner <linkId> there.).
  3. All signing happens locally inside @oakagentkit/addon. The Oak server never sees your key and never signs or sends a transaction. Your swaps and deposits go straight from your wallet to the project; subscription payments go to the burner (OakBurner) and the single-owner treasury wallet. Hosted non-read tool requests use a 15-minute wallet-signed X-Oak-Session plus a 60-second single-use X-Oak-Request signature from an ephemeral in-memory sessionKey. Gloam relay and deposit attribution carry no session or request signatures; only public proof fields or a public shield hash reach those routes.
  4. Always inspect the preview. Every transaction tool call runs preview (eth_simulateV1 with traceTransfers: true) before signing and sending, and reuses a matching preview from the same block within 12 seconds so swap does not re-simulate twice. Built approvals are always exact (amountIn), never unlimited. Note that simulation transfers exclude gas and do not prove off-chain external settlement (such as Relay destination fills or Meridian RFQ relayer execution).
